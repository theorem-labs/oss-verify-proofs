# tools/oft

The tools of this repository: Python 3, PyYAML and, for `./oft lint`, idna
(`requirements.txt`, pinned by hash), nothing else.  Run them as
`./oft <command>` from the repository root.

| command | what it does |
|---|---|
| `./oft generate [--check]` | renders every generated file from the facts; `--check` compares instead of writing, and is what CI runs |
| `./oft lint [--changed-only BASE] [--jobs N]` | the repository's rules (below); when the text rules read 256 files or more they run on every CPU the process may run on (its affinity set, so `taskset` narrows it; `--jobs` sets the number of processes, 1 or more), and the findings do not depend on it; `--changed-only` runs the per-file text rules (`private-data`, `links`, `proofs`) only over the files that differ from commit `BASE`, and reports an unused exception only for a path that differs from it, or, saying so on stderr, runs them over every file when a fact (a file [`paths.py`](paths.py) classes as facts), a finding's `finding.yaml`, a `.gitattributes`, [`lint-exceptions.yaml`](lint-exceptions.yaml) or the running tools (this directory, when it is inside the tree) differ from it, since these decide what a file may hold; the rules over the whole tree still run. It needs `--root` at the top of a git checkout and a `BASE` that names a commit, and fails otherwise. Its verdict on an unchanged file is the one that file had at `BASE`, so it is only as good as a whole lint of `BASE`: `pr.yml` passes it for a pull request into main, which every push linted whole, and lints every file for a pull request into any other branch |
| `./oft ledger --base REV [--tip REV]` | the findings ledger over the history `REV..TIP` (below) |
| `./oft fetch <project>...` | downloads a project's binaries from its release asset and checks the archive's SHA-256 and every file's; `--findings` fetches the unpatched binaries its findings run on instead, into `findings/<project>/bin/` |
| `./oft verify-sha <project>...` | checks fetched binaries against their `harness.yaml` |
| `./oft check <project>/<harness>...` | builds the images and statements and has the kernel type each statement `harness.yaml` lists that `Statements.v` carries and print what they assume, checks every proof through a wrapper and every assumption the wrapper prints against `toolchain/allowed-axioms.txt`, and re-runs every counterexample; `--parts findings` re-runs every finding on the unpatched binaries and compares each run with its record, and `--record` prints the runs of a finding that has none yet, only when its input shows each statement false and its control shows none false; `--rocqchk` adds an independent re-check with `rocqchk`, which can take hours for one proof and is not part of the verdict. Without `--parts` it checks each of statements, proofs and counterexamples that the unit has. It fails on a unit it examined nothing in: one whose `Statements.v` is missing, lacks one of those statements, states one as an axiom (`Axiom`, `Parameter`, `Admitted`) or makes them assume an axiom outside the allowlist, or has none to define (each withheld or withdrawn), and one with no proof when `--parts` names proofs (`ci/check-units.sh` checks the units a job's `proof_units` leaves out with `--parts statements`). CI runs it as `python3 -m oft.check`, which loads the checker and none of the other commands' modules |
| `./oft plan [--base REV] [--pr-kind KIND] [--store REV] [--units FILE] [--explain PROJECT/HARNESS]` | the parts CI checks, as JSON for its job matrix. Each part of each harness (`build`: its statements and proofs, for a harness with published builds and a statement `Statements.v` carries; `counterexamples`; `findings`) has a content key: the SHA-256 of the git object ids, and the checkout attributes, of what that part's check reads, with the checker image or the runner image and the checker itself, every file of `tools/` but the files of `tools/oft/` that `keys.NOT_THE_CHECKER` names ([keys.py](keys.py)). A part is checked when its key has no recorded pass at `--store`, a commit of the branch `check-results`, and, with `--base`, when its key differs from its key at the base: so a change is checked on what it changes, and a change to a file no check opens checks nothing. For `--pr-kind maintainer` or `contributor` the statements are the base's, as `pr.yml`'s check job takes them; `--tools REV` names the tools the check jobs run (default: the base, else `HEAD`). Each part's row says why it is or is not checked; `--explain` prints one harness's rows with every input of each key. Each job lists its `check_units` (whose build it checks) and, of those, its `proof_units` (with a proof of one of their statements) |
| `./oft release-tree` | turns a checkout into the files of a release, in place: keeps the proof of each statement `approvals.yaml` lists, with its fuzz target's whole `lib/` and build record, removes every other proof; leaves out what the hold (`facts.hold`) holds back: by one removal path, turns each project held whole (`release: private` in its `project.yaml`, or a finding `patched` or `reported`, or `open` in a project that is not enrolled) that OSS-Fuzz has into a held project (its `project.yaml` rewritten to `schema`, `project`, `homepage`, `language`, `oss_fuzz`, `status: held`, `reason: held`, and the rest of `projects/<p>/`, its `counterexamples/<p>/`, `patches/<p>/`, `notes/<p>.md` and proofs removed), and removes whole one OSS-Fuzz does not have (a held page for a project never released would tell the reader that a finding exists), printing `held back by a finding that is not public: <project>` for each project a finding holds whole; for an enrolled project (`enrolled: true`) whose holding findings are all `open`, removes only the statements they name and every agreement or halts statement their recorded input shows false, with each held agreement's bound and decidability statements, their proofs and counterexamples (a hold that would leave a harness with no statement, or a harness that publishes a build with only withheld statements, or in a project with a proof library, `proofs/<p>/<h>/lib/`, which ships unchecked, or in one with a published binary that `findings/<p>/unpatched.yaml` does not pin as the one its findings run on, holds the whole project instead); writes `release.yaml`'s `counts` and `oss_fuzz.projects` as the cut leaves them, and drops each `image_libraries` entry no build of the cut links; removes `findings/` entirely and the files only this repository has (`approvals.yaml`, `.github/CODEOWNERS`, `.github/workflows/facts-review.yml`, `.claude/skills/review-facts/SKILL.md`, `review.md`, `.github/workflows/enroll.yml`, `.github/workflows/enroll-build.yml`, `tools/enroll/`, `.github/workflows/proof-index.yml` and `.github/proof-index.py`); rewrites `tools/oft/lint-exceptions.yaml` without each entry whose path is at or under a path the cut removes (the lines above its `exceptions` key stay as written); renders again and prints the cut's statement counts for its CHANGELOG section; it reports a listed statement with no proof, each fuzz target whose `lib/` it keeps while removing some of its statement directories, and each file in `proofs/lib/`; and it changes nothing, since every check runs before the first change, when the facts have an error (an entry of a held or private project, a held statement or a listed refutation among them), the checkout holds a symbolic link outside an ignored path, a path the cut removes is a symbolic link (an ignored one, `projects/<p>/bin/` or a `_build/` of a held project, among them), git tracks a file at an ignored path, `proofs/` holds a stray file, a kept statement directory holds anything but `Proof.v`, `proof.yaml` and `dune`, the facts as the release will have them have an error, a holding finding's evidence cannot be read within its cap, the generated files are not current, or a file the release keeps or writes (the held page, a rewritten `harness.yaml`, the rewritten `lint-exceptions.yaml`, `release.yaml` and every generated file, as the cut's facts render them) discloses what is held back, whole or in part, and each refusal names the file, the kind of what it holds and the finding or project it belongs to. That search ([`disclosure.py`](disclosure.py)) reads nothing when nothing is held, and otherwise runs on lint's forked file scanner, so a worker that dies fails the cut. What it catches is a closed list, frozen on 2026-10-26: `findings/` never ships, a held project is removed or cut to its held page, and every release pull request is reviewed, so the search is a safety net for the common accident. It catches a copy of a holding finding's evidence (1) whole, or any part of 32 or more letters and digits, or a whole short unit (a hunk's lines, its added text or its removed text, or a printable run of 8 or more characters of an input's payload); (2) with changes of white space, line endings, case or Unicode normal form; (3) in UTF-8, UTF-16 or UTF-32; (4) through HTML character references, percent escapes and the backslash escapes of C, Python, JSON and YAML, octal and YAML's `\0`, `\a`, `\e` and `\_` among them; (5) with the line prefixes of Markdown quoting and code comments; (6) as hex in the layouts of `xxd -p` and `xxd` (with item 5's marks on each line, too), and as a C array of bytes (`xxd -i`, Python's `hex()`, or decimal items); and (7) by an input's exact bytes or its SHA-256; and it catches the names below. Each item applies on its own: a combination of items is out of scope, and so is everything else: word and colour diffs, quoted-printable, a URL query's `+` for a blank, the layouts of `od` and `hexdump`, per-line decorations such as `cat -n`, `cat -A`, `git blame` and `git grep`, base64 (YAML's `!!binary` among them), and anything retyped or paraphrased. It reads each file's text by its byte order mark, or as UTF-8 and as UTF-16 and UTF-32 from every offset, with HTML character references, percent escapes and backslash escapes (JSON's `\uXXXX`, and `\f`, `\v`, `\b`, `\a`, `\e`, `\0` and YAML's `\_`, `\N`, `\L` and `\P` as the characters they stand for, among them; a backslash before an octal digit as C and Python read it, and, when an input holds a NUL before an octal digit, also as YAML reads `\0` then; a backslash before a line break keeps the break, and the bytes below join the lines) decoded until nothing changes (at most eight rounds, by a decoder that never raises: a numeric reference of more than seven digits after its leading zeros stays as it is), NFKC-normalised and case-folded, and compares it in three forms. In the long form, only its letters and digits, so comment prefixes (`//`, `#`, `*`, `>`, `|`), quotes, doubled quotes, punctuation, white space, zero-width characters and soft hyphens all read the same, it compares evidence in windows: every run of 32 characters of a holding finding's summary (whole and each sentence), of each patch's subject and commit message, of each hunk's removed lines joined and of its added lines joined, of each hunk's new side (its context and added lines in file order) where the run holds a character the change adds or spans the place of one it removes, of the printable text of each input's payload, and of the hex of each input and each digest, is a key of one hash table, except a run of fewer than 8 different characters, which is chance text, and a run made only of the outcome vocabulary (`disclosure.OUTCOME_WORDS`: build names, outcomes, connectives and digits), which every counterexample note writes; a 16-character index of the windows is probed every 17 positions of a file's long text and each hit is checked against the windows around it, so every 32-character copy is found, and the upstream context lines a harness quotes never count by themselves. In the punctuation form, each line without the marks a copy puts at its ends (diff's `+`, `-`, `<` and `>`, a reply quote's `>`, a table's `|`, a comment's `#`, `//`, `*`, `;` or `(* *)`, a string's quotes; a backslash before a line break keeps the break here, so each line keeps its marks) and then without white space, with a run of one quote read as one, short evidence counts whole, from 8 characters and whatever its characters: each hunk's lines in diff order (context included), its removed text and its added text, and each printable run of each input's payload, so a fix of a few characters and a reproducer that is mostly punctuation count; it counts in the plain form too, the text without white space alone, so a copy rewrapped, or folded by YAML's writer, counts where a new line begins with a character a mark would take (`(*t`). In the bytes a file spells, one byte per character (its own; the text of each decoding round, and of each decoder alone, so that none reads the bytes another wrote, a backslash before a line break there joining the lines and the blanks after it, as YAML's writer folds a string; `\0` before an octal digit read as YAML reads it, a NUL and the digit, when an input holds that byte pair; percent escapes read one byte each; each of these with adjacent string literals joined and with each `0xNN` or `0xN` item of a C array read as its byte, and as it is; and the bytes of its `xxd` and `xxd -p` lines and of its decimal arrays in brackets or braces), each input's bytes and every run of 32 of them with at least 8 different bytes count, so a copy as Python's `repr`, a C string of `\x` or octal escapes, YAML's escapes and this repository's YAML writer, percent escapes, `xxd`, `xxd -p` or `xxd -i` writes it counts. An input that is the driver's header alone counts not at all, and neither does the SHA-256 of empty output. It looks for names at a name boundary, so that a prefix of another name never matches and a name followed by a source or header suffix (`openssl/x509.h`) is read as a file's name, in the file's path and its text with each path resolved (`.`, `..`, repeated slashes), each line break and each blank beside a `/` deleted, and every dash read as `_`: each fuzz target of a project held whole, as `<project>/<harness>` and as its Rocq module with or without `OssFuzzTheorems.`; the slug, each patch file name (every `*.patch` of its directory, whether or not a field names it) and each recorded output digest of a finding that holds its project back, and the SHA-256 of each non-empty input; each held statement as `<project>/<harness>/<statement>`, by its Rocq names with or without the root, as `<harness>/<statement>` (not after a `/`, where it ends another fuzz target's name), and, in a file of its own fuzz target (under its directories or the project's notes, or one that names its Rocq module), as `<statement>` or `<statement>_holds` |
| `./oft approvals FILE --approved-by LOGIN --date DATE` | writes `approvals.yaml`: one entry for each line of FILE whose fuzz target has a proof in the checkout: a line with a submission's record names the proofs that record covers (it must name them, and each must be a statement of the fuzz target), a bare line names every other proof of its fuzz target; a fuzz target may have one bare line and record lines with different records and disjoint statements; a refutation, or a fuzz target of a private project, is never listed; a fuzz target of a project a finding holds back is omitted and printed as `held by a finding that is not public: <project>/<harness>`, and a statement an open finding of an enrolled project holds back as `held by an open finding: <project>/<harness>/<statement>` (a line whose every proof is held gets only those lines); an existing entry for the same fuzz target, origin and record whose content is unchanged keeps its approver and date |
| `./oft revisions PREVIOUS [--write-pins] [--earlier OLDER...]` | fingerprints this tree and `PREVIOUS`, a checkout of the previous release, with the same tools, and gives each statement's meaning (same, changed, re-rendered: these tools render other code for it than `PREVIOUS`'s did, or model-changed: the model's name, version or commit, or the Rocq package or version, differs), the revision it must have and what happens to its proof; fails when a revision is wrong; `--write-pins` sets the pin of each proof that carries forward to its statement's fingerprint here; `--earlier` names the releases before `PREVIOUS`, strictly newest first (by date, and on one date by release, a candidate `-rc.N` by N and before its release; another order compares nothing), so that a statement `PREVIOUS` left out (held back by a finding, or private) is compared with the newest of them that has it instead of counting as new ([docs/versioning.md](../../docs/versioning.md)) |

## The facts, and what is rendered from them

The facts are `release.yaml`, `projects/<project>/project.yaml`,
`projects/<project>/<harness>/harness.yaml` (with the harness's `source/`
copy and `Distribution.v`), and the proof and counterexample directories.
Their schemas are in [`schemas/`](schemas/), in a small closed vocabulary
that [`schema.py`](schema.py) reads: any key a schema does not list is an
error.  [`rules.py`](rules.py) adds the rules that relate one fact to
another; among them, a statement's name follows from its fields, and the
header of `Distribution.v` must agree with the definitions in its body.

From the facts, `generate` renders `Statements.v`, `Characterise.v`,
`Images.v`, `images/dune`, the per-harness `dune` file, the opam files,
`dune-project`, every README, `index/`, and the header of each
`Distribution.v`.  All of the prose is in [`templates/`](templates/) and
[`phrasebook.yaml`](phrasebook.yaml); [`shapes.py`](shapes.py) is the one
place that maps a statement's fields to the definition of
`theories/Shapes.v` it uses, and refuses a combination it does not list.
Rendering is deterministic, and `render_all` is importable, so a tree and its
preview are rendered by the same code.

Proved, refuted and counterexample statuses are never written in the facts:
they follow from `proofs/` and `counterexamples/`.

`approvals.yaml`, in a checkout that has one, lists the proofs a release
carries, by fuzz target and statement, with one entry per source of a fuzz target's proofs
([`schemas/approvals.yaml`](schemas/approvals.yaml)). `./oft release-tree`
removes it, so a release never holds it.

A finding, a library bug found while proving, is kept on the proof branch as
`findings/<project>/<harness>/<slug>/`: `finding.yaml` (the statements it shows
false, its state, its summary, its patch and its recorded runs),
`input.bin`, `control.bin` and its patch.  `findings/<project>/unpatched.yaml`
pins the binaries built without the patches, which the findings run on, and
`findings/<project>/<harness>/series` lists the patches in build order.  A
finding's `input.bin` and `control.bin` are whole driver inputs, header and
payload, so they may be as large as 1 MiB (a harness may read a payload of 64
KiB or more); every other file of `findings/` is at most 64 KiB.  A
finding is never deleted.  It stops holding its project only through a checked
state change to `pruned`, `not-a-defect` or `public`.  No rendered file reads
`findings/`, and it never ships: `./oft release-tree` removes it.  A project
with a finding that is `patched` or `reported` ships only as `status: held`,
`reason: held`.  An enrolled project (`enrolled: true` in its `project.yaml`)
whose holding findings are all `open` ships without the statements they name, and without any their recorded input shows false (with each held agreement's bound and decidability statements). The whole project is held instead if that would leave a harness with no statement, or a harness that publishes a build with only withheld statements, if the project has a proof library (`proofs/<p>/<h>/lib/`, which ships unchecked), or if it publishes a binary that `findings/<p>/unpatched.yaml` does not pin as the one its findings run on, since that build may carry the fix;
once one is `patched` or `reported`, its binaries carry the fix, and the whole
project is held.  A state never returns to `open` from `patched`, `reported` or
`public`, whose patch the pinned build carries; it may from `pruned` or
`not-a-defect`.

A proof branch takes pushes and merges, so a finding could be added and then
deleted or rewritten between the two trees a pull request compares.
`./oft ledger` judges the history instead.  A record (a directory with
`finding.yaml`) is anchored at its first version that is evidence, decided by
its own files alone: its `input.bin` and `control.bin` are regular files of at
most 1 MiB that begin with a complete driver header, each of its `statements`
is an agreement or halts statement by its name, and its input and control each
hold a run of every build those statements name, of the shape `oft check
--record` prints.  Any recorded runs of that shape anchor a record, whether or
not they show its statements false, so a record's runs must come only from
`oft check --record`, which prints them only when each run has that shape (no
timeout, no signal a finding does not record), the input shows each statement
false and the control shows none.  No schema, `harness.yaml` or
`unpatched.yaml` decides it, so neither another file nor a later change to
the tools turns evidence back into a draft.  Before its anchor a record is a
draft, which CI never re-ran, and may change in any way or be renamed or
deleted.  Anchors are found by ancestry, and two that differ in `input.bin`,
`control.bin`, `statements` or recorded runs are refused.  From its
anchor on, every file of the record that a commit of `BASE..TIP` or a parent
of one had is in `TIP`; its `input.bin` and `control.bin` are the anchor's, its
`statements` include the anchor's, and the unpatched pin of each build its
statements name keeps its first value after the anchor (a pin for another
build may be added).  Its recorded runs are the anchor's too: a push to a
proof branch runs no check, so a pin in the anchor commit may already name a
fixed binary, and the same binaries in the same runner give the same runs.
Only a new runner image can change an honest record's runs.  A record anchored
outside `BASE..TIP` is held to where `TIP`'s history meets `BASE`.  For each
merge base of the two (`git merge-base --all`; more than one only after a
criss-cross merge), its entry commit is the oldest commit of `BASE`'s
first-parent line that has it, which passed CI as long as `BASE` takes changes
only through checked pull requests (a branch rule on `BASE` enforces that, not
these tools).  The merge base alone may be a proof-branch commit that no check
judged, put right before main merged it.  So the reference is the merge base
when its entry commit has the same runner and recorded runs (its text may
differ), and otherwise the newest commit of that line that `TIP` has, since
the entry commit then holds main's changes too.  In a pull request both are
`BASE`; on a push to a proof branch, a
branch that lags main is held to what it has.  The record keeps the runs each
reference has, except one whose `images.runner` in `release.yaml` (the image CI
re-runs findings in) differs from `TIP`'s, as in lint's base comparison.  A
record anchored only in `BASE..TIP` keeps its anchor's runs whatever the
runner, since that commit's `release.yaml` was not checked either.  If a new
runner changes such a
record's runs, CI's re-run fails, so its branch cannot merge and its project
stays held.
Each parent of a merge counts.  The rule is net: only `TIP` is judged, so a
file beside a record that `paths.py` does not list (an old `run.sh`) may go,
and restoring what was deleted clears the finding.  No replace ref or graft is
read.  CI runs it in a pull request's lint job and on every push to a
`proofs/` branch, where a forced push fails: a proof branch is never
rewritten.

## The rules (`./oft lint`)

| rule | what | where it runs |
|---|---|---|
| `paths` | every path matches exactly one entry of [`paths.py`](paths.py), which says who owns it; CI compares the proposed findings ledger with its trusted base, file by file, so a finding and its unpatched pins are never deleted, moved or renamed, a base finding's `input.bin` and `control.bin` and the unpatched pin of each build its statements name never change, nor do its recorded runs of those builds unless the proposed `release.yaml` pins another runner image, its `statements` only grow, and its state never returns to `open` from `patched`, `reported` or `public` (its state may otherwise change, from `pruned` or `not-a-defect` back to `open` too, as may its summary, `upstream` and patch text, and a pin for another build may be added), and `./oft ledger` holds every commit of the change's history to the same rule from each record's anchor, its first version whose `input.bin` and `control.bin` are regular files that begin with a complete driver header and whose `finding.yaml` names agreement or halts statements only and records a run of every build they name, of the shape `oft check --record` prints (a draft before it may change, be renamed or be deleted, two anchors of one record that differ are refused, and only a record anchored in the base's history may record its runs again under another runner image); every finding file is a bounded regular file before the loader reads it, so links and special files are refused before their target can be opened; exported facts change only in a release pull request; a contributor's pull request touches only `proofs/`, `counterexamples/`, `docs/` and generated files; no `.vo`, `.hex`, `.pyc`, ELF file, LFS pointer, symbolic link or other file that is not regular (none is followed, opened or read for the text rules); no LFS filter or `working-tree-encoding` in `.gitattributes` (a checkout in another encoding would hide a file's text from the text rules); no name with a `"`, a `\` or a control character (git lists such a name quoted, and CI could not judge it); notes only for listed projects; size caps (a file over its cap is not read for the text rules) | CI |

| `private-data` | in every NUL-free file read as text, link or not: no host path, private key, access token, or `theorem-labs` repository outside the public ones (among them the OSS Verify port, `theorem-labs/oss-verify`) named as `theorem-labs/<name>` or `theorem-labs.github.io/<name>` (after `/`, `\` or `:`, in any case, also written with `%2F` or a character reference, or, in a file GitHub renders as Markdown, split by a backslash escape or an HTML comment); the port's internal copy is allowed only as the value of a held project's `build.oss_verify.repository`. | `links` | links in the files this repository wrote, in the port's files of a port build record, and in an OSS Verify target's source copy, as a regular expression reads them (in a file whose name GitHub renders as Markdown, in any case, also the forms GitHub renders as a link, and each line read again as GitHub shows its text, without backslash escapes and HTML comments), judged by what a browser opens, as [`urls.py`](urls.py) parses it after the WHATWG URL standard: never a machine on a private network, including through a non-web scheme with a DNS-shaped or IP-literal host, and a `theorem-labs` repository, on any host, only if it is a public one; a URL whose host IDNA refuses is a finding; in rendered text, docs and facts every link is one the facts record or a fixed public one (the Debian snapshot archive, which the runner image installs from, may be read over http). Markdown HTML reads `href`, `src`, `srcset`, `cite` and `longdesc` | CI |
| `free-text` | no free-text field that the rendering has no place for | CI |
| `proofs` | no `Axiom`, `Parameter`, `Admitted`, `admit`, plugin, file effect or `Unset ... Checking` in `proofs/`, and no `Load`, `Cd` or `Extra Dependency` in a generated Rocq file of `projects/` (comments and strings are skipped by a real lexer; in `proofs/`, a notation token or a comment that could make Rocq lex them otherwise is refused, and a reviewed entry in [`lint-exceptions.yaml`](lint-exceptions.yaml) that names one such token exactly (path, line, message, its string literal, count 1) clears it; an entry less exact, or one no finding matches, is a finding; in either, a Rocq file that is not text is refused); no wall-clock limit in a Rocq file of the repository (`proofs/`, `theories/`, `projects/`, `tests/` and the `.v.tmpl` templates): no `timeout` or `timeoutf` used as a name, Ltac2's `Control.timeout` and `Control.timeoutf` among them, no `Timeout <n>` and no `Set Default Timeout <n>`, unless the line that has it ends with `(* timeout-ok: <why> *)` saying why an expiry cannot fail the check, which a reviewer judges; and a Ltac2 `@external` binds only a primitive of `lint.EXTERNAL_ALLOWED`, which no such comment clears ([docs/proving.md](../../docs/proving.md)); the wrapper's `Print Assumptions` and the allowlist are the authority | CI |

Every rule fails when it examined nothing.  The tests in [`tests/`](tests/)
plant a positive for each rule and require it to fail, and require the
fixture tree and this repository itself to pass.  On a pull request, `pr.yml`
skips the test of this repository when the change leaves `tools/` as it is
outside the test data in `tests/` (no Python file), `ci/` and this README, and
leaves `.github/` and every `.gitattributes` as they are: its lint job then runs
the same code over the same tree.  A push to main runs it.

## CI

The workflows in `.github/workflows/` run these tools from the base branch,
never from the pull request (`pr.yml`); [`ci/check-units.sh`](ci/check-units.sh)
is the part every check job shares: fetch by SHA-256, build and check in the
checker image with no network, and the counterexamples and the findings in the
runner image. In `pr.yml` and `release-check.yml`, the `fetch-drafts` job is
the one job with write access: it reads draft releases' binaries only, and the
check jobs read them from its artifacts.  (`release.yml`'s publish job has write
access too.)  `pr.yml`'s jobs and what each one covers are described at the top
of the workflow.

## Tests

    cd tools && python3 -B -m unittest discover -s oft/tests -t .

One process per test class, which is how `pr.yml` runs them (on 16 CPUs, about
60 s in one process and 11 s this way, without the whole-tree lint test, which
takes about 5 minutes by itself).  It prints every class's output whole, in one
order whatever order the processes end in, and exits 1 naming every test that
failed:

    cd tools && python3 -B -m oft.tests.parallel [--jobs N]
