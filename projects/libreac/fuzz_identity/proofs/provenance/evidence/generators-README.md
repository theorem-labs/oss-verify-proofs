# gen_ro_redzones.py — the generator of record for `lib/{A,B}/Rt/RoRedzones.v`

Those two files are generated, not written. This directory holds the generator so a reader of the shipped
tree can reproduce them, because the header line inside each file names it.

## What it produces

`lib/A/Rt/RoRedzones.v` and `lib/B/Rt/RoRedzones.v`: the redzone bytes of the READ-ONLY registered ASan
globals — the descriptors of the `asan_globals` section whose object lies in `.rodata`, over
`[beg + size, beg + size_with_redzone)` — as constant cells in the `rodata_chk` shape, each value read
from the image itself. The check in each file compares every cell with the image segments by `vm_compute`.

## The images, by sha256

The generator bakes in no paths: `--img-a`, `--img-b`, `--pin-a` and `--pin-b` are required. The run of
record used these four images, named here by content so the record does not depend on any machine:

| flag | build | sha256 |
| --- | --- | --- |
| `--pin-a` | `fuzz_identity.asan` (pinned) | `c954b804786cb87fc218414447199e35235b9788453ec0db312f97cd0dc4291b` |
| `--pin-b` | `fuzz_identity.asan-ubsan` (pinned) | `baf1a4d065e02f55521d39f05d8c8d9ed763a0ef798c70cc3eabe5816ffb3f66` |
| `--img-a` | `fuzz_identity.asan` (unstripped twin) | `98c4713d9086` (prefix; the twin of the pin above) |
| `--img-b` | `fuzz_identity.asan-ubsan` (unstripped twin) | the twin of the `--pin-b` image |

The two pin sha256s are the values `harness.yaml` records for the `asan` and `asan-ubsan` builds, so the
images are identified by the same digests the unit is pinned to.

## The command

```
python3 provenance/evidence/gen_ro_redzones.py \
    --img-a <unstripped asan> --img-b <unstripped asan-ubsan> \
    --pin-a <pinned asan>     --pin-b <pinned asan-ubsan> \
    --out-a <dir A> --out-b <dir B>
```

It writes `RoRedzones.v` into each `--out-*` directory and prints what it measured; the run of record
printed `A: 50 descriptors, 46 read-only globals, 1384 redzone bytes, 0 not 0x00 in the pinned ELF`.

## Its test, which lives with the tool

The owner keeps `test_gen_ro_redzones.py` (`8a9b72a394ea`) beside the generator in the tool registry of
record, at `tools/gen_ro_redzones/55074e3279be/`. It checks that the emitted header names the tool and no lane,
worker, author or path, and that the generator's own source carries no host path. It is deliberately NOT
shipped here: it holds the host-path patterns it searches for as literals, so shipping it would put the
very strings it exists to forbid into the released tree — the scanner of record flags it for exactly that.
Run it from the tool's own directory, passing this unit's committed files:

```
python3 test_gen_ro_redzones.py --gen gen_ro_redzones.py \
    --committed-a <unit>/lib/A/Rt/RoRedzones.v --committed-b <unit>/lib/B/Rt/RoRedzones.v \
    --img-a … --img-b … --pin-a … --pin-b …
```

It reports `PASS: gen_ro_redzones.py (0 failure(s))` on `55074e3279be` and fails on both earlier versions.

## Why this generator is here at all

Its header template used to emit an internal lane identity instead of the tool's own name, into both
generated files. A lane name is an internal working identity and does not belong in released text, and
removing it from the files alone would not have held: the next regeneration writes the header again. The
template now emits `Generated by gen_ro_redzones.py`, and the generator travels with the unit so the
name it emits resolves to something a reader can open.

Both files were REGENERATED from the pinned images rather than edited, and each differs from its previous
committed version in that one header line only.
